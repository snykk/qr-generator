# QR Decoder — Arbitrary-Angle Robustness Plan

This document describes the implementation plan for **arbitrary-angle finder detection** targeting the `v0.13.0` minor release. It extends the decoder to locate a symbol tilted or rotated well past the ~30-degree band the current 1:1:3:1:1 line scanner handles, closing the last listed decoder limitation. This is the hardest milestone so far — it is computer vision, not spec transcription — so the plan is honest about the approach, the validation, and where the scope boundary realistically sits.

> Status: **draft / living document.** Milestones DR1..DR5 land incrementally on the `decoder-robustness` branch; each is a focused commit (or small commit series) with tests, matching the cadence used for the prior milestones.

> Indonesian version: [docs/plan-decoder-robustness.id.md](plan-decoder-robustness.id.md).

## 1. Vision & Goals

- Decode QR photos taken at a steep angle — the tilt band where the current pipeline fails — without any caller intervention, the same way v0.4 rotation handling and v0.3 adaptive thresholding are automatic.
- Fix the stage that actually breaks under perspective. The plan first assumed it was finder detection; measurement showed it is the **affine three-centre homography**, which cannot undo perspective keystoning (section 2). So the milestone estimates a **projective homography from the finder corners** and leaves finder detection to a connected-component pass that supplies those corners.
- Keep the fast path fast: the projective pipeline runs as a **fallback**, only when the affine decode fails, mirroring the Otsu -> Sauvola fallback (doc 14). Upright and rotated symbols keep their current speed and results.
- Keep **zero runtime dependencies**: the detector and the homography solver are pure Go; the tilt test fixtures are generated by an in-tree image warp, with no OpenCV or `x/image`.
- Be **honest about limits**. CV is empirical: the milestone widens the working band and documents the angle range it actually clears on synthetic fixtures, rather than claiming universal robustness.

## 2. Why decoding fails under tilt, and the fix

> Course correction (found empirically during implementation). The original plan assumed finder detection is the bottleneck: that the **1:1:3:1:1** line scan (`fitsFinderRatio`, +-50% per module) breaks under perspective foreshortening past ~30 degrees. Measured against synthetic tilt fixtures, that was wrong in two ways. First, the line scan's loose tolerance keeps finding all three finders to ~55 degrees. Second, and decisively, decoding fails from ~20 degrees up **even when the finders are found** — because `homographyFromFinders` builds an **affine** map from three finder centres, and an affine map cannot undo perspective keystoning. A control test confirms it: sampling the same tilted fixtures with a ground-truth **projective** homography decodes cleanly to 70 degrees. So the real blocker is the geometry stage, not finder detection.

The robust fix is a **projective homography estimated from the finder-pattern corners**. A projective transform is exactly the map between a plane and its perspective image; it needs four-plus non-degenerate correspondences. The three finder centres give only three imperfect points (a finder's centroid is not a projective invariant), but each finder is a square with four corners, so three finders give twelve corner correspondences spread across the symbol. The pipeline becomes:

1. Locate the finders by **connected-component** analysis (two-pass union-find + the dark/light/dark nesting with 7:5:3 bounding-box sides), which the labelling also lets us revisit for corners. This reaches the same ~55 degrees the line scan does; beyond that neither detects finders.
2. Extract each finder's four outer-ring corners (farthest-point method, rotation-agnostic) and assign each its module coordinate via the symbol's axes.
3. Solve a **least-squares projective homography** over the twelve corners (`computeHomographyLS`, normal equations).
4. Because version cannot be read reliably from a foreshortened symbol, seed it from the finder-quad edge length and **trial** nearby versions, letting Reed-Solomon validation pick the one that decodes.
5. Wire the whole thing as a **fallback**: `decodeImage` runs the unchanged affine pipeline first and only falls back to the projective one when that cannot decode, so upright and rotated symbols are byte-for-byte unaffected.

## 3. Scope

### In scope for v0.13.0

- A connected-component finder detector (`qrgen/decode_finder_cc.go` or similar): two-pass CCL, hole/nesting analysis, concentricity and area-ratio matching, producing `finderCandidate` centres compatible with the existing `finderTriple` pipeline.
- Wiring it as a **fallback** in `decodeImageDebug`: try the fast line scanner first; on failure, run the component detector before giving up. A new `binariserUsedState`-style note may record which detector succeeded, for tests.
- Synthetic-tilt test fixtures: an in-tree image warp that renders a QR and projects it at a chosen tilt/rotation, plus round-trip decode tests across a range of angles that establish the working band.
- Reference doc `docs/theory/24-arbitrary-angle-detection.md` (EN + ID), and a README/limitations update reflecting the new band.

### Out of scope (still)

- **Universal robustness.** This is best-effort CV: heavy blur, glare that destroys a finder's nesting, folds/curves, or near-90-degree grazing angles may still fail. The doc states the measured band.
- **Multi-symbol detection** (several QR codes in one image). One symbol, as today.
- **Tunable Sauvola parameters and morphological cleanup.** A separate robustness lever (the other half of the roadmap item); deferred to keep this milestone on the finder detector.
- **A new public API.** `Decode`/`DecodeBytes` gain the capability transparently; no signature change.

## 6. Risks & Technical Notes

- **This does not fully close, and that is documented.** Unlike a spec feature, a CV pipeline has no guaranteed success rate. The band is empirical (section DR4 Checkpoint A) and orientation-dependent; the README and theory doc state it honestly rather than claiming universal robustness. It is a real improvement — decoding that previously failed from ~20 degrees now reaches ~35-55 — not a complete solution.
- **The bottleneck was geometry, not detection.** The original assumption (that the finder line scan fails first) was disproven by measurement; the affine three-centroid homography is what caps the old pipeline, and finder centroids are not projective invariants. The fix estimates a projective transform from twelve finder corners instead.
- **Version under perspective.** The finder spacing foreshortens and the bounding-box module estimate inflates, so the version estimate is unreliable. Mitigated with a corner-edge seed and a proximity-ordered version trial gated by Reed-Solomon, which makes a wrong version fail fast and the right one decode.
- **Fallback keeps the fast path.** The projective path (CC labelling plus a bounded version trial) is more expensive than the affine pipeline, so it runs only when the affine decode fails. Upright and rotated symbols never pay for it, and existing decode tests and timings are unaffected.
- **Test-fixture warp is not the product.** The tilt warp lives in tests only; it fabricates inputs to prove the pipeline, and its own sampling quality only affects how hard the test images are, not the library.

## 8. Open Questions

To be answered before the corresponding milestone starts:

- **Detector algorithm.** Two-pass union-find CCL with hole analysis (proposed) versus a per-candidate multi-directional ratio test at component centroids. The topological approach is more perspective-robust; confirm in DR3.
- **Finder signature thresholds.** The concentricity tolerance and the acceptable area-ratio deviation for the 7:5:3 nesting — tuned against the synthetic fixtures in DR3/DR4.
- **Fallback vs. always-run.** Proposed: fallback only when the line scanner fails, to protect the fast path. Confirm this does not miss cases where the line scanner returns a wrong (not empty) triple; if so, consider running both and reconciling.
- **Claimed band.** Which angle range the README/doc will state as reliably decoded, set empirically from DR4's results rather than asserted up front.

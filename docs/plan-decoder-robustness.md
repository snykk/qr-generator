# QR Decoder — Arbitrary-Angle Robustness Plan

This document describes the implementation plan for **arbitrary-angle finder detection** targeting the `v0.13.0` minor release. It extends the decoder to locate a symbol tilted or rotated well past the ~30-degree band the current 1:1:3:1:1 line scanner handles, closing the last listed decoder limitation. This is the hardest milestone so far — it is computer vision, not spec transcription — so the plan is honest about the approach, the validation, and where the scope boundary realistically sits.

> Status: **draft / living document.** Milestones DR1..DR5 land incrementally on the `decoder-robustness` branch; each is a focused commit (or small commit series) with tests, matching the cadence used for the prior milestones.

> Indonesian version: [docs/plan-decoder-robustness.id.md](plan-decoder-robustness.id.md).

## 1. Vision & Goals

- Decode QR photos taken at a steep angle — the 30..90-degree band where the current finder scanner fails — without any caller intervention, the same way v0.4 rotation handling and v0.3 adaptive thresholding are automatic.
- Do it by fixing the **one** stage that fails at steep angles: **finder detection**. Everything after it (finder ordering, version estimate, homography, module sampling) is already a projective transform and handles arbitrary tilt; only the 1:1:3:1:1 line scan that locates the finders breaks under strong perspective. So the milestone adds a rotation-and-perspective-invariant finder detector and reuses the existing geometry pipeline unchanged.
- Keep the fast path fast: the new detector runs as a **fallback**, only when the existing line scanner fails to find three finders, mirroring the Otsu -> Sauvola fallback (doc 14). Upright symbols keep their current speed.
- Keep **zero runtime dependencies**: the detector is a pure-Go connected-component pass; the tilt test fixtures are generated by an in-tree image warp, with no OpenCV or `x/image`.
- Be **honest about limits**. CV is empirical: the milestone widens the working band and documents the angle range it actually clears on synthetic fixtures, rather than claiming universal robustness.

## 2. Why the current detector fails, and the fix

The current `findFinders` scans image rows (and cross-checks columns) for five runs matching the **1:1:3:1:1** ratio (`fitsFinderRatio`, +-50% per module). A finder pattern is concentric squares, so a straight line through its centre crosses that ratio at any *rotation* — which is why v0.4 already handles rotation up to ~30 degrees. What breaks it is **perspective foreshortening**: past ~30 degrees of tilt the crossing lengths are compressed unevenly, the measured ratio drifts outside the tolerance band, and no run of five qualifies. Widening the tolerance would swamp the detector with false positives.

The robust fix is to stop measuring a 1-D ratio and instead detect the finder's **topological structure**, which a projective transform preserves. A finder is a solid dark centre inside a light ring inside a dark ring — three nested regions with concentric centres and area ratios near 3x3 : 5x5 : 7x7. Nesting and concentricity survive any homography, so a **connected-component** analysis finds finders at any angle:

1. Label the dark connected components of the binarised image (two-pass union-find).
2. For each dark component, find the light component it encloses and the dark component enclosed within that (the component hierarchy / holes).
3. Accept the triple as a finder candidate when the three centroids coincide (within tolerance) and the nested areas match the 7:5:3 structure within tolerance.
4. Return the candidate centres, which feed the existing `orderFinderTriple` -> `estimateVersion` -> `homographyFromFinders` -> `refineHomography` -> `sampleMatrix` pipeline exactly as the line scanner's output does today.

## 3. Scope

### In scope for v0.13.0

- A connected-component finder detector (`qrgen/decode_finder_cc.go` or similar): two-pass CCL, hole/nesting analysis, concentricity and area-ratio matching, producing `finderCandidate` centres compatible with the existing `finderTriple` pipeline.
- Wiring it as a **fallback** in `decodeImageDebug`: try the fast line scanner first; on failure, run the component detector before giving up. A new `binariserUsedState`-style note may record which detector succeeded, for tests.
- Synthetic-tilt test fixtures: an in-tree image warp that renders a QR and projects it at a chosen tilt/rotation, plus round-trip decode tests across a range of angles that establish the working band.
- Reference doc `docs/theory/24-arbitrary-angle-detection.md` (EN + ID), and a README/limitations update reflecting the new band.

### Out of scope (still)

- **Universal robustness.** This is best-effort CV: heavy blur, glare that destroys a finder's nesting, folds/curves, or near-90-degree grazing angles may still fail. The doc states the measured band.
- **Multi-symbol detection** (several QR codes in one image). One symbol, as today.
- **Tunable Sauvola parameters and morphological cleanup.** A separate robustness lever (the other half of the roadmap item); deferred to keep this milestone on the finder detector.
- **A new public API.** `Decode`/`DecodeBytes` gain the capability transparently; no signature change.

## 6. Risks & Technical Notes

- **This may not fully close.** Unlike a spec feature, a CV detector has no guaranteed success rate. The plan mitigates by (a) keeping it a fallback so nothing regresses, and (b) validating on synthetic fixtures and reporting the actual band rather than a claim. If the component detector clears, say, 30..70 degrees but not 70..90, that is the documented result and still a real improvement.
- **False positives.** Loosening finder detection risks accepting non-finders. The nesting + concentricity + area-ratio tests are stricter than a 1-D ratio, and three mutually-consistent finders (via `orderFinderTriple` and `estimateVersion`) must agree, so a stray candidate is filtered downstream.
- **Fallback keeps the fast path.** The component pass (CCL over the image) is more expensive than a few row scans, so it runs only when the line scanner fails. Upright and mildly-tilted symbols never pay for it, and existing decode tests and timings are unaffected.
- **Homography already handles perspective.** The milestone deliberately does not touch `homographyFromFinders`/`refineHomography`; they already fit an arbitrary 3x3 projective transform from the finder centres, so once the centres are found at a steep angle the rest just works. The alignment-pattern refinement (v0.4) further corrects perspective.
- **Test-fixture warp is not the product.** The tilt warp lives in tests only; it fabricates inputs to prove the detector, and its own quality (nearest vs bilinear sampling) only affects how hard the test images are, not the library.

## 8. Open Questions

To be answered before the corresponding milestone starts:

- **Detector algorithm.** Two-pass union-find CCL with hole analysis (proposed) versus a per-candidate multi-directional ratio test at component centroids. The topological approach is more perspective-robust; confirm in DR3.
- **Finder signature thresholds.** The concentricity tolerance and the acceptable area-ratio deviation for the 7:5:3 nesting — tuned against the synthetic fixtures in DR3/DR4.
- **Fallback vs. always-run.** Proposed: fallback only when the line scanner fails, to protect the fast path. Confirm this does not miss cases where the line scanner returns a wrong (not empty) triple; if so, consider running both and reconciling.
- **Claimed band.** Which angle range the README/doc will state as reliably decoded, set empirically from DR4's results rather than asserted up front.
